# `data/` — Brod Alarm Data Contract

This directory is the **single source of truth** for all data the Brod Alarm frontend renders. Every file here is also mirrored to `public/data/*.json` so Next.js serves it directly at `/data/*.json` (no API routes needed).

Pipeline owner: data engineer. Consumer: frontend. **If the schema changes here, update `Brod Alarm.md` Section 9 in the same commit.** This is enforced by `AGENTS.md`.

---

## Files

| File | Source | Refresh trigger |
|---|---|---|
| `cruises.json` | Scraped from `cruisetimetables.com` | `npm run scrape` in `scripts/` |
| `zones.json` | Generated by `npm run zones:import` from `zones.geojson` | Edit `zones.geojson`, re-import |
| `zones.geojson` | Hand-authored or via geojson.io | Manual edit |
| `forecast.json` | Derived: `cruises.json` + `zones.json` + open-meteo | `npm run forecast` in `scripts/` |
| `recommendations.json` | Hand-authored copy bank (HR + EN) | Manual edit |

To rebuild everything from scratch: `cd scripts && npm run build:data`.

### Editing zones visually with geojson.io

```bash
cd scripts
npm run zones:export        # writes data/zones.geojson with 1 dock point + 5 zone polygons
# 1. Open geojson.io, drag data/zones.geojson onto the page
# 2. Edit polygons (click to enter edit mode, drag vertices, add points)
# 3. Drag the cruise_dock point if the dock origin is wrong
# 4. Save → Save as GeoJSON → overwrite data/zones.geojson
npm run zones:import        # regenerates data/zones.json from geojson (geojson is SoT)
npm run sync                # mirrors zones.json to public/data/
npm run forecast            # recomputes data/forecast.json with new geometry
```

`zones-import-geojson.ts` rules:

- The dock origin can be either a Polygon with `id="cruiser_dock"` (centroid used) or a Point with `id="cruise_dock"`.
- Each destination polygon needs `properties.id` (canonical: `port`, `old_town`, `west_coast`, `beaches`, `malls`). Legacy aliases (`ferry_port`, `bacvice_beach`, `mall_of_split`) are automatically migrated.
- `properties.type` is honoured if present (one of `transport_hub`, `historic_center`, `indoor_shopping`, `local_refuge`, `beach`); otherwise a default is assigned per canonical id.
- Adding a wholly new zone requires (a) a canonical `id`, (b) a `type`, and (c) an entry in `BASE_SHARE` in `scripts/lib/heuristic.ts`. The import will fail loudly otherwise.

## Schema reference

Canonical TypeScript types + Zod runtime schemas live in `scripts/lib/types.ts`. The summaries below are for frontend developers who just need to know the shape.

### `cruises.json`

```ts
{
  $schema_version: 1,
  generated_at: string,            // ISO 8601 UTC
  source: "cruisetimetables.com",
  year: number,                    // e.g. 2026
  ships: Array<{
    id: string,                    // stable, e.g. "2026-05-16_msc-armonia"
    date: string,                  // "YYYY-MM-DD"
    ship_name: string,
    cruise_line: string,
    arrival_time: string | null,   // "HH:MM" or null when source said "early morning" etc.
    departure_time: string | null, // "HH:MM" or null
    passengers: number             // integer, total passenger capacity
  }>
}
```

### `zones.json`

```ts
{
  $schema_version: 1,
  cruise_dock: { lat: number, lng: number },     // origin point — start of dot-animations
  zones: Array<{
    id: "port" | "old_town" | "west_coast" | "beaches" | "malls",
    name_hr: string,
    name_en: string,
    center: { lat: number, lng: number },        // centroid; drop-zone for dot-animations
    polygon: Array<[number, number]>,            // GeoJSON [lng, lat], closed ring
    distance_from_cruise_dock_m: number,         // informational only (NOT used by algorithm)
    type:
      | "transport_hub"
      | "historic_center"
      | "indoor_shopping"
      | "tourist_promenade"
      | "local_refuge"
      | "beach",
    access_mode: "walking" | "vehicular"         // FE animation hint, not algorithmic
  }>
}
```

### `forecast.json` (the deliverable the UI renders)

```ts
{
  $schema_version: 1,
  generated_at: string,
  based_on: {
    cruises_generated_at: string,
    zones_version: number
  },
  time_slots: Array<{                            // 30-min slots, 7-day horizon
    datetime: string,                            // ISO with offset, e.g. "2026-05-16T10:00:00+02:00"
    weather: {
      temp_c: number,
      wind_kmh: number,
      precip_mm: number
    } | null,                                    // null if open-meteo was unavailable at gen time
    weather_bucket: "rain" | "hot_sunny" | "strong_wind" | "cool_cloudy" | "default",
    ashore_count: number,                        // total passengers ashore at this slot (integer)
    ships_in_port: string[],                     // ship ids currently in port
    zones: Record<string, {                      // keyed by zone.id
      load: number,                              // estimated passengers in zone (integer)
      share: number,                             // 0..1, normalised allocation share
      level: "green" | "yellow" | "orange" | "red",
      density_pph?: number,                      // optional: passengers per hectare (basis for `level`)
      contributing_ships: string[]               // ship ids that contribute (= ships_in_port)
    }>
  }>
}
```

**Conservation invariant:** `Σ_zones zones[z].load ≈ ashore_count` for every slot. If the sum drifts more than a few units, that's a rounding artefact, not a model bug.

### `recommendations.json` (copy bank for the UI)

```ts
{
  $schema_version: 1,
  business: Record<string, { hr: string, en: string }>,
  local: Record<string, { hr: string, en: string }>
}
```

Template tokens like `{ship_name}` `{time}` `{zone_name}` are substituted client-side.

Current keys:
- `business`: `imminent_ship`, `multi_ship_day`, `calm_window`, `no_ships_today`
- `local`: `zone_red`, `zone_orange`, `zone_safe_window`, `alternative_zone`, `all_clear_today`

## How the frontend consumes this

Static fetches in any React component / route handler:

```ts
const forecast = await fetch("/data/forecast.json").then((r) => r.json());
const zones    = await fetch("/data/zones.json").then((r) => r.json());
const copy     = await fetch("/data/recommendations.json").then((r) => r.json());
```

Or, for build-time embedding, import the JSON from `public/data/*.json`.

If type safety is desired on the frontend, copy `scripts/lib/types.ts` into the frontend (or symlink it). The schemas + types are exported.

### Hint for the "dots walking from the dock" animation

The data contract already supplies everything needed for a real-time passenger-flow simulation:

- **Spawn point:** `zones.cruise_dock` (lng, lat).
- **Destinations:** `zones[z].center` per zone.
- **How many dots per zone at each slot:** `forecast.time_slots[i].zones[z].load`.
- **When dots actually exist:** `forecast.time_slots[i].ashore_count` (rises from 0 over the ramp-up, peaks during plateau, *dips at lunch*, falls during ramp-down — see Heuristic § Disembarkation Curve + Lunch Dip).
- **Travel time anchor by access mode:**
  - `access_mode: "walking"` → use ~80 m/min (tourists with bags). E.g. `old_town` (939 m) ≈ 12 min walk.
  - `access_mode: "vehicular"` → use ~500 m/min (≈30 km/h city traffic). E.g. `malls` (4 098 m) ≈ 8 min by bus / taxi / Uber / Bolt. Cruise tourists do **not** walk 4 km to the mall — render this as bus/taxi animation, or simply teleport with a short delay.

The pipeline does not produce per-dot trajectories — that's purely an FE rendering concern. Interpolate dot positions between consecutive 30-min slots client-side. Respect `access_mode` for visual honesty.

**Map page (`/map`):** On narrow viewports the time slider shows only the first **2 days** of slots (96×30 min) so markers stay readable. Timeline ship markers use `cruises.json` times when present; missing `arrival_time` / `departure_time` use the same **08:00 / 17:00** defaults as `scripts/lib/heuristic.ts` and are labelled *procijenjeno* in the UI. Touch: zone details open via Leaflet **popup** (tap polygon); ship details open in a **bottom sheet** fixed to the safe area.

## Load thresholds (for UI colour coding)

Severity is derived from **passenger density**: `load / zone_polygon_area`
→ **passengers per hectare** (pax/ha, one hectare = 10 000 m²). Polygon area is computed in `scripts/lib/geo.ts` (planar projection at mean latitude — appropriate for city-scale zones). This makes a compact old town and a sprawling port **comparable**: the same absolute `load` can be yellow in one polygon and green in another.

Each zone row in `forecast.json` may include optional `density_pph` (same as pax/ha, rounded to one decimal) for tooltips.

| Level | Density (pax/ha) | UI hint |
|---|---|---|
| `green` | `< 12` | Calm |
| `yellow` | `12–35` | Building |
| `orange` | `35–90` | Heavy |
| `red` | `≥ 90` | Extreme |

If polygon area is missing or zero, the pipeline falls back to absolute head-count bands in `scripts/lib/heuristic.ts` (`LEVEL_THRESHOLDS_ABSOLUTE`).

Constants live in `scripts/lib/heuristic.ts` (`DENSITY_THRESHOLDS_PAX_PER_HA` + fallback table) and should match anything the UI renders.

## Heuristic explanation (for the pitch)

The model is an **allocation with conservation**, not a multiplicative spillover. At every 30-min slot it produces a single number per zone — and the sum of those numbers equals the passengers actually ashore. No overcounting, no opaque tuning.

### The formula

```
ashore_from_ship(t)   = passengers × ASHORE_RATE × disembarkation_curve(t)
ashore_count(t)       = Σ_ships  ashore_from_ship(t)

raw_share(z)          = BASE_SHARE[z] × WEATHER_MODIFIER[type(z)][bucket(weather(t))]
share(z)              = raw_share(z) / Σ raw_share

load(z, t)            = ashore_count(t) × share(z)
```

### Calibrated constants (defendable, all centred inside literature ranges)

**`ASHORE_RATE = 0.75`** — fraction of total ship capacity that goes ashore at a port-of-call. Source: CLIA *State of the Cruise Industry* annual reports + Stefanidaki & Lekakou (2014), *Cruise carrying capacity: a conceptual approach*. Published Mediterranean range 60–90 %; we use the central value.

**`BASE_SHARE`** — steady-state distribution of ashore passengers across destination zones in calm/dry/mild weather. Sums to exactly 1.0.

| Zone | base_share | Source band |
|---|---|---|
| `old_town` | 0.67 | 65–80 % Med-port "iconic centre" (CLIA, Castillo-Manzano & López-Valpuesta 2018) |
| `port` | 0.12 | 8–15 % port-area lingering (shore-excursion meetups, late returners) |
| `beaches` | 0.08 | 5–15 % warm-season beach-going (Croatian Bureau of Statistics, TZ Split) |
| `west_coast` | 0.08 | 5–12 % secondary promenade share (hotels, beach bars, ~15-min scenic walk) |
| `malls` | 0.05 | 3–10 % good-weather shopping (rises sharply in rain — see modifier) |

**`WEATHER_MODIFIER`** — multiplicative adjustment per zone *type* per weather bucket. Applied to `BASE_SHARE`, then renormalised so shares still sum to 1.

| weather bucket | `transport_hub` | `historic_center` | `indoor_shopping` | `tourist_promenade` | `local_refuge` | `beach` |
|---|---|---|---|---|---|---|
| **rain** (precip ≥ 0.5 mm/h) | 1.10 | 1.10 | **3.50** | 0.40 | 0.55 | 0.10 |
| **hot_sunny** (temp ≥ 28 °C, dry) | 1.00 | 0.85 | 0.70 | 1.30 | 1.10 | **1.80** |
| **strong_wind** (wind ≥ 30 km/h) | 1.00 | 1.00 | 1.05 | 0.55 | 0.80 | 0.45 |
| **cool_cloudy** (15–22 °C, dry) | 1.00 | 1.10 | 1.10 | 0.95 | 1.00 | 0.55 |
| **default** (everything else) | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |

Modifier sources:
- Beach rain × 0.10, hot+sunny × 1.80: Moreno & Amelung (2009), climate-tourism research on Mediterranean beaches; reported attendance swings of −70 to −90 % in rain, +50 to +150 % in optimal conditions.
- Mall rain × 3.50: published Med-port shopping uptake spikes 2.5–4× in adverse weather (Barcelona, Palma studies); conservative-mid of that band.
- Tourist_promenade rain × 0.40, hot_sunny × 1.30: exposed scenic walk; less hit than the beach (people still walk briefly in light rain), bigger boost than historic_center in good weather (recreational walking peaks in mild warm weather).
- Historic_center rain × 1.10: small positive (people seek shelter in Palace arcades and covered Riva sections) — documented "indoor refuge" effect in urban tourism climatology.
- Wind effects: Croatian tourism climate research on bura/jugo wind events; beach attendance halves, exposed waterfront promenades nearly halve, sheltered zones unaffected.

### `disembarkation_curve(t, dwell, localHour)` — when ashore passengers are actually off the ship

Two components multiplied together:

1. **Trapezoidal envelope** — a function of how long the ship has been in port: 90-minute linear ramp-up from arrival, plateau at 1.0, 60-minute linear ramp-down before departure. Constants: `RAMP_UP_MINUTES = 90`, `RAMP_DOWN_MINUTES = 60`. Source: Dowling, *Cruise Ship Tourism* (port operations chapter); CLIA observed disembarkation patterns.

2. **Lunch dip** — a function of local clock hour. Cruise lines actively promote ship-board lunch (free buffet vs €30+ shore restaurants), and 30–40 % of ashore passengers return to ship between roughly 11:30 and 14:30. We use a 35 % return rate (`LUNCH_DIP_FLOOR = 0.65`):

```
1.00              before 11:30
1.00 → 0.65       linear ramp, 11:30 → 12:00
0.65              flat, 12:00 → 14:00      (≈35 % aboard for lunch)
0.65 → 1.00       linear ramp, 14:00 → 14:30
1.00              after 14:30
```

Sources: CLIA passenger-behaviour reports on shore-spending patterns; Stefanidaki & Lekakou (2014) on dual-peak port-call activity at Med ports; field observations at Dubrovnik / Kotor / Korčula. The lunch valley is observable in the generated `ashore_count` series — at 12:00 the total ashore drops to 65 % of the morning peak across all ships in port.

### Bucket-resolution priority

A weather slot is classified into exactly one bucket. Priority (highest first):

1. `rain` if `precip_mm ≥ 0.5`
2. `strong_wind` if `wind_kmh ≥ 30`
3. `hot_sunny` if `temp_c ≥ 28`
4. `cool_cloudy` if `15 ≤ temp_c ≤ 22`
5. `default` otherwise

Implemented in `weatherBucket()` in `scripts/lib/heuristic.ts`.

### Tuning policy

Every constant lives in **one file**: `scripts/lib/heuristic.ts`. Changing the model is a one-line edit. If you change `BASE_SHARE`, the values must continue to sum to 1.0; the import script warns (does not fail) when they don't.

If Split-specific survey data becomes available (e.g. TZ Split publishes a cruise-passenger destination breakdown), replace the relevant `BASE_SHARE` entries and update the citation comment in `heuristic.ts`. The algorithm itself does not change.

## Weather provenance

`scripts/generate-forecast.ts` fetches hourly weather from **[open-meteo.com](https://open-meteo.com)** — a real production weather API (not a stub).

- **Endpoint:** `https://api.open-meteo.com/v1/forecast`
- **Coordinates pinned:** `latitude=43.5081, longitude=16.4402` (Split centre)
- **Variables:** `temperature_2m`, `wind_speed_10m`, `precipitation` (hourly)
- **Timezone:** `Europe/Zagreb`
- **Auth:** none required, no rate-limit issues at our scale
- **Source data:** aggregated from ECMWF (European Centre for Medium-Range Weather Forecasts — the gold-standard global model), DWD (German national weather service), Met Norway, NOAA GFS. Same upstream data used by paid services like OpenWeatherMap and Weatherbit.
- **Resolution:** ~9 km grid (HRES model)
- **Failure mode:** if the API is unreachable at generation time, the forecast still ships with `weather: null` and `weather_bucket: "default"` for each slot. Rerun `npm run forecast` later to backfill.

Citable phrasing for the pitch: *"open-meteo.com, which serves ECMWF / DWD national-weather-service data without a paywall."*

If we ever need to swap to the Croatian state hydro-meteorological institute (**DHMZ**, meteo.hr) as the primary, only `fetchWeather()` in `scripts/generate-forecast.ts` needs to change. The data contract above is unaffected.
